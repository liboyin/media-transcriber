## MLX smoke test

**Status:** done on 2026-11-17, before T3 (adapter interface) and T5 (MLX adapter). The user authorized and ran it on the Mac and reported the output.

Purpose: learn whether full `large-v3` fits in memory on the M2 Mac (DESIGN M15) and how fast MLX Whisper runs, before the T5 boundary is written.

Environment: Apple M2 with 16 GiB, macOS 27.2.1, real Metal accelerator. Python 3.14.10, mlx 0.32.4, mlx-whisper 0.4.3, installed by `uv run --no-project --with mlx-whisper==0.4.3` outside the repository. No repository code ran. Model `mlx-community/whisper-large-v3-mlx` at revision `49e6aa286ad60c14352c404340ded53710378a11`, a 3.1 GB `weights.npz` with 32 decoder layers and no quantization, downloaded into a local directory.

Method: a throwaway script called `mlx_whisper.transcribe` twice with `language="en"` and the local model directory, then wrote the segments as SRT. The first call included the model load. Each timed call included mlx-whisper's own ffmpeg decoding. Input: one English review video of 49.6 seconds, converted to mono 16 kHz WAV. It was not from the video library, and its hash was not recorded.

| Run | Wall time | Peak MLX memory | Segments |
|---|---|---|---|
| Cold, with model load | 13.0 s | 3.43 GiB | 12 |
| Warm | 10.0 s | 3.43 GiB | 12 |

- The warm real-time factor is about 0.20, or about 5 times real time. The model load added about 3 seconds.
- The user read the SRT and judged it correct.
- `/usr/bin/time -l` reported a maximum resident set size of 0.94 GB. MLX buffers in unified memory are not fully counted there, so the MLX peak is the better measure.

Limitations: one short clip, one run of each kind, an unrecorded power source and no Chinese clip. The numbers show fit and rough speed only. They are not benchmark evidence under DESIGN section 7, and they do not choose a default profile (M5). The install size of mlx-whisper with its torch dependency was not measured.

## SMB hard links

From [T6](../closed/T6.md#host-checks): on the Mac, create a file in a hidden scratch directory at the staging root, hard-link it, confirm that a second link fails with "File exists", and remove the directory. `NEVER` publication through `StagedFile` needs hard links and has no fallback. The user authorized the check.

**Result:** failed, on 2026-11-18 (Mac clock). The user ran it on the M2 Mac against the staging share mounted at `/Volumes/libo-smallfiles/Transcode`. No accelerator was used.

- `ln` failed with "Operation not supported", both times. The file `a` kept a link count of 1.
- The scratch directory was removed.
- A second check the same day, through Python on the Mac, tested `renamex_np` with `RENAME_EXCL`. It returned `EEXIST` onto an existing file, which kept its content. It returned `ENOTSUP` for a rename to a new name, so the mount does not support an exclusive rename. `open` with `O_EXCL` returned `EEXIST` on an existing file, as required. The scratch directory was removed.
- A third check the same day tested a plain `os.rename`. It replaced an existing file, and it renamed a file to a new name. The scratch directory was removed.
- Effect: `NEVER` publication through `StagedFile` cannot publish on the Mac's SMB mount. DESIGN 5.6 needs a new decision before T7. Until then, T6's publication works only on filesystems with hard links.

**Linux result:** passed, on 2026-11-18 (host clock). The user ran the same `ln` check on the future CUDA machine, a Linux host, against the staging share mounted at `/media/libo-smallfiles/Transcode`. No accelerator was used.

- The first link succeeded. The second link failed with "File exists".
- Both names showed inode 10182 with a link count of 2. The scratch directory was removed.
- Effect: the Linux CIFS mount supports hard links, so `NEVER` publication there uses links and not the fallback of DESIGN M21. The CUDA deployment's Docker bind mount of this share sees the same mount (DESIGN M15).

After [T12](../closed/T12.md), publication falls back to a check and a rename on this share (DESIGN M21). Still open: once the service exists (T7, T11), publish one SRT on the real Mac share through `publish_srt`, and confirm that it appears whole and that an existing SRT is kept.
